# {{PROJECT_NAME}} — Domo Pro-Code App

> Instructions for AI coding agents (Claude Code, Cursor, Codex, Antigravity, Copilot, Gemini…).
> `CLAUDE.md` imports this file, so every agent reads the same rules.

This is a **Domo custom app** (a "pro-code" app / App Framework design) scaffolded
with [create-dovite](https://github.com/Ajay-Balu/create-dovite):
**Vite + React + TypeScript + Tailwind CSS v4 + shadcn/ui + ryuu.js**.

The app is a static single-page app. `{{RUN}} upload` builds it and publishes the
`dist/` folder to Domo with the Domo CLI (`ryuu`). Inside Domo it renders as a
**card in a sandboxed iframe** — read "Running inside Domo" before writing UI,
navigation, storage or data code.

## How to work on this project (read first)

You are building a Domo app for a developer who may not know every Domo limit.
Act as a **Domo solution architect**, not just a code generator:

1. **Plan before coding.** For a new app, feature or significant change, open
   `.claude/skills/domo-app-planning/SKILL.md` and follow its protocol: spot the
   platform constraints in the request, ask only the questions that change the
   design, then present a short plan with **recommendations** and wait for a yes.
   Example recommendations:
   - "This needs a Salesforce API key, which can't live in the browser. I suggest a
     **Code Engine** function (no credits) called via `runCodeEngine`. Shall I write it?"
   - "It will be **embedded in your website** with per-customer filters; the SQL API
     ignores those filters, so I'll use `queryData` (Data API) instead. OK?"
   - "The SQL API can't JOIN. Create a Magic ETL output and I'll map that one dataset."
2. **Load the skill for the job** (below) before writing Domo-specific code. Don't
   guess manifest keys, endpoints or limits — check the skill's `references/`; if
   it isn't covered, say it's unverified.
3. **Build** with this project's conventions (API layer, manifest, iframe rules below).
4. **Hand off**: list exactly what the developer must do in Domo (IDs to fill in the
   manifest, card wiring, Code Engine package, `proxyId`, version bump, publish).

## Running inside Domo (iframe rules)

The published app runs in an iframe on a separate origin
(`*.domoapps.*.domo.com`) embedded in a Domo page/card. Consequences:

- **All Domo data goes through `ryuu.js`** (wrapped in `src/API/domoApi.ts`).
  ryuu.js talks to the parent page, which handles auth. Never use `fetch`/`axios`
  against Domo URLs, never store tokens, never put client IDs/secrets in the
  front end (anything shipped is public). Use **Code Engine** for secrets,
  external APIs or Domo public APIs (`api.domo.com`).
- **Navigation:** the iframe can't navigate the Domo page. Use `navigate(url, newWindow)`
  from the API file (wraps `domo.navigate`). External links need `target="_blank"`
  + `rel="noopener noreferrer"`. In-app routing must be hash-based or in-memory
  (no server rewrites exist in Domo).
- **Size:** card size comes from `manifest.json → size` (Domo grid units) or the
  page layout. Build responsive layouts that fill the iframe (`h-full`, `min-h-0`,
  internal scroll areas). Don't assume a desktop viewport; check `domo.env.platform`
  (`"desktop" | "mobile"`).
- **Assets:** import them through Vite or put them in `public/`; external
  resources must be `https://` and CORS-enabled.
- **Storage:** `localStorage`/cookies are third-party in an iframe and may be
  partitioned or blocked. Persist anything important in **AppDB**.
- **Safari / iOS / embedded (Domo Everywhere):** when cross-site cookies are blocked
  (Safari, iPhone/iPad, in-app web views, hardened browsers) most cookie-based Domo
  features stop working. Never depend on cookies: keep all calls in `domoApi`
  (ryuu.js sends the session header), use programmatic filters for embeds, and test
  on Safari/iOS. Details: `domo-everywhere-embed` skill.
- **Dialogs:** `alert`/`confirm`/`prompt` and popups may be blocked by the sandbox.
  Use in-app modals (shadcn/ui `Dialog`/`AlertDialog`).
- **Dataset updates:** by default Domo reloads the app when a mapped dataset
  updates. Register `onDataUpdated((alias) => …)` to refresh data yourself instead.
- **Page filters & variables:** listen with `onFiltersUpdated(cb)` /
  `domo.onVariablesUpdated(cb)` (the first `onFiltersUpdated` registration
  **clears** the page's filters); push filters with
  `domo.requestFiltersUpdate(filters, pageStateUpdate)`. Page filters and embed
  filters apply to the **Data API** (`queryData`/`fetchData`), **not** to SQL (`fetchSqlData`).
- **Environment:** `getEnv()` (`domo.env`) gives `userId`, `customer`, `locale`,
  `pageId`, `platform`… from URL params — fine for UI, **not for security**
  (spoofable). Verify identity with `GetCurrentUser()`.
- **Embedding other Domo cards/dashboards** inside this app means a nested
  iframe (Domo Embed / embed URLs). You can't read or style its DOM; size the
  container explicitly and pass filters via the embed API, not the DOM.

## manifest.json

`public/manifest.json` is copied to `dist/` at build time. It is the contract
between the code and Domo — **every alias used in code must exist here.**

```jsonc
{
  "name": "{{PROJECT_NAME}}",
  "version": "0.0.1",
  "size": { "width": 3, "height": 3 },   // card size in Domo grid units (1–6)
  "fullpage": true,                       // iframe follows the window in details/mobile view
  "id": "…",                              // added on first publish — keep it (see Publishing)
  "proxyId": "…",                         // card id used by the local proxy for AppDB/workflows/Code Engine
  "mapping": [                            // datasets → used by fetchData / fetchSqlData
    {
      "alias": "sales",
      "dataSetId": "00000000-0000-0000-0000-000000000000",
      "fields": [
        { "alias": "region", "columnName": "Region" },
        { "alias": "amount", "columnName": "Sales Amount" }
      ]
    }
  ],
  "collections": [                        // AppDB collections → CreateDocument / QueryDocument …
    {
      "name": "tasks",
      "syncEnabled": true,                // also write to a Domo dataset
      "schema": { "columns": [ { "name": "title", "type": "STRING" } ] }
    }
  ],
  "workflowMapping": [ /* { "alias": "email", "modelId": "…", … } → startWorkflow / sendEmail */ ],
  "packagesMapping": [ /* { "alias": "myFn", "parameters": […], "output": {…} } → runCodeEngine */ ],
  "allowCamera": false,                   // device permissions: set true only what you need
  "allowMic": false,
  "allowGeolocation": false,
  "allowBluetooth": false,
  "allowNFC": false
}
```

Rules:
- Use exactly these key spellings: `mapping` (or `datasetsMapping`), `collections`
  (or `collectionsMapping`), `workflowMapping`, `packagesMapping` — **not**
  `packageMapping`/`workflowsMapping` even though some Domo docs show them.
  Full reference: `.claude/skills/domo-procode-apps/references/manifest.md`.
- Dataset `alias`es and `fields[].alias` are what the code uses — never the dataset ID
  or raw column names. `fetchData` only returns mapped fields.
- AppDB `schema.columns[].type`: `STRING | LONG | DECIMAL | DOUBLE | DATE | DATETIME`.
- Workflow and Code Engine entries have more fields (parameters, output, version).
  Don't invent IDs — ask the user or copy them from Domo (App Studio / the card's
  wiring screen / the Code Engine package page).
- Remove example entries you don't need: an invalid mapping fails `domo publish`.

## API layer — `src/API/domoApi.ts`

The single place for Domo calls. Add new endpoints here (not in components) and
reuse the internal `enc`/`toQueryString`/`fail` helpers. Named exports and a
default `DomoApi` object are both available:

```ts
import { fetchSqlData, CreateDocument } from "@/API/domoApi";
// or: import DomoApi from "@/API/domoApi"; DomoApi.fetchSqlData(...)
```

| Area | Functions | Endpoint |
| --- | --- | --- |
| User | `GetCurrentUser`, `GetUser`, `ListAllUsers`, `GetAllUser` | `/domo/environment/v1`, `/domo/users/v1` |
| Datasets | `queryData(alias, options)`, `fetchData(alias, query?)`, `fetchSqlData(alias, sql)` | `domo.data.query`, `GET /data/v1/:alias`, `POST /sql/v1/:alias` (text/plain) |
| AppDB | `CreateDocument`, `ListDocuments`, `GetDocument`, `UpdateDocument`, `partialUpdateDocument`, `DeleteDocument`, `BulkDeleteDocuments`, `QueryDocument`, `queryDocumentsByDate`, `queryDocumentsWithAggregations` | `/domo/datastores/v1/collections/:name/documents…` |
| Files | `UploadFile`, `UploadRevision`, `GetFile` | `/domo/data-files/v1` |
| AI | `fetchAIData(prompt, template?, maxWords?)` | `POST /domo/ai/v1/text/generation` |
| Workflows | `startWorkflow(alias, body)`, `sendEmail(...)`, `DataflowsActions(...)` | `POST /domo/workflow/v1/models/:alias/start` |
| Code Engine | `runCodeEngine(alias, input)` | `POST /domo/codeengine/v2/packages/:alias` |
| Iframe / events | `navigate(url, newWindow)`, `getEnv()`, `onDataUpdated(cb)`, `onFiltersUpdated(cb)` | `domo.navigate`, `domo.env`, domo.js events |

Notes:
- **Data API vs SQL:** `queryData`/`fetchData` respect page filters and embed
  filters; `fetchSqlData` does **not**, and has no JOINs. Default to `queryData`;
  use SQL only for standalone apps that need expressions the Data API lacks.
- `fetchData` query string uses Domo's data API params:
  `fields=a,b&filter=amount>100&groupby=region&orderby=amount descending&limit=100`.
- In `fetchSqlData` the **table name is the dataset alias**: `SELECT region, SUM(amount) AS total FROM sales GROUP BY region`.
  One call = **one dataset** (the alias in the URL): no JOINs/UNIONs across datasets
  (build a Magic ETL / DataSet View and map its output instead), but **subqueries on
  the same alias work**: `SELECT * FROM sales WHERE amount > (SELECT AVG(amount) FROM sales)`.
- **Domo uses UTC.** Dates/datetimes from datasets, SQL, AppDB (`createdOn`,
  `updatedOn`) and workflows are UTC. Send UTC ISO-8601 (`new Date().toISOString()`)
  in filters, queries and writes; convert to the viewer's time zone only when
  displaying (`Intl.DateTimeFormat`, locale from `getEnv()`). Watch day boundaries
  ("today" in IST starts at 18:30 UTC the day before).
- AppDB documents look like `{ id, createdOn, updatedOn, owner, content: {…} }`.
  Queries use **MongoDB syntax** on `content.<field>`:
  `QueryDocument("tasks", { "content.status": { $in: ["open", "blocked"] }, createdOn: { $gte: { $date: "2026-11-01T00:00:00Z" } } })`.
  Filter on the server with `QueryDocument` rather than `ListDocuments` + JS filtering;
  updates use `partialUpdateDocument` with `$set` / `$inc` / `$push`.
- `sendEmail` / `DataflowsActions` start the workflows aliased `email` / `dataflow`
  (pass another alias as the last argument).
- **Code Engine** is the answer for secrets, external APIs and anything only a Domo
  Product API can do: inside a function, `codeengine.sendRequest('GET', '/api/...')`
  needs **no instance domain and no developer token**, Node built-ins (`crypto`…) are
  available, and it costs no credits. Keep only real entry points as top-level
  functions; put helpers in a class (`domo-code-engine` skill → "Code structure").
- ryuu.js v6 also has typed helpers (`domo.data.query`, `domo.appdb.*`,
  `domo.ai.generateText`, `domo.workflow.start`, `domo.codeEngine`) — fine to use
  inside the API file, but keep components calling `domoApi` functions.
- Every function logs `[domoApi] <name>` and **re-throws** — handle errors
  (loading/error/empty states) in the UI.

## Current user context

`src/API/currentUserContext.tsx` loads the Domo user once. `<UserProvider>` is
already wired in `src/main.tsx`; read the user in any component:

```tsx
import { useCurrentUser } from "@/API/currentUserContext";
const { currentUser, currentUserId, avatarKey, loading, error } = useCurrentUser();
```

`avatarKey` is a Domo-relative URL (`/domo/avatars/v2/USER/:id`) usable in `<img src>`.

## Local development

1. `domo login` (once per instance).
2. `{{RUN}} dev` — `vite.config` mounts `@domoinc/ryuu-proxy`, which forwards
   `/domo/*`, `/data/*`, `/sql/*` to your instance using the CLI login.
3. The proxy needs the app published at least once (manifest `id`).
   AppDB, workflows and Code Engine also need `proxyId` = the id of a card
   created from this design (the id after `/kpis/details/` in the card URL).
- `Not authenticated. Please login using "domo login"` → run `domo login`.
- 404/403 on a dataset → alias missing from `mapping`, or app not republished after a manifest change.

## Publishing

1. `{{RUN}} upload` runs `scripts/upload.mjs`, which:
   - **bumps `version` in `public/manifest.json` automatically** — patch +1, patch and
     minor roll over after 9: `0.0.1 → 0.0.2 … 0.0.9 → 0.1.0 … 0.9.9 → 1.0.0`; the
     major number keeps growing (`9.9.9 → 10.0.0`);
   - runs the build, then `domo publish` from `dist/`;
   - **rolls the version back** if the build or publish fails;
   - after the first publish, **copies the design `id`** Domo wrote into
     `dist/manifest.json` back into `public/manifest.json` — commit it.
   Options: `{{RUN}} upload -- --no-bump` (republish the same version),
   `{{RUN}} upload -- --dry-run` (show the next version).
2. Don't bump `version` by hand before uploading, and never edit `dist/manifest.json`
   (`package.json` version doesn't matter to Domo).
3. Create a card from the design in Domo (Asset Library → your design) and wire
   datasets/collections if prompted.

## Rules for Claude

- Follow the "How to work on this project" protocol: recommend first, build after agreement.
- Keep all Domo calls in `src/API/domoApi.ts`; components call those functions.
- Never hardcode dataset IDs, tokens, client secrets or instance URLs in source.
- When code needs a new dataset/collection/workflow/Code Engine function, add the
  alias to `public/manifest.json` too, and tell the user which IDs they must fill in.
- Don't edit generated files in `src/components/ui/` unless asked; re-add via CLI.
- Don't add `axios` or other HTTP clients for Domo; don't add a router that needs
  server rewrites (use hash/memory routing).
- Handle loading, empty and error states for every data call; Domo calls can be slow.
  `DomoAuthError` (401/403) extends `DomoHttpError` — check it first.
- Aggregate on the server (`queryData` with `groupBy`/`sum`, SQL `GROUP BY`); never
  pull large datasets into the browser to sum them.
- Before adding a metered feature (AppDB sync, workflows, AI, extra ETL outputs),
  mention its credit impact (`domo-credit-consumption`).
- Design for the iframe: responsive, no `window.top`, no `alert()`, external links in new tabs.
- Run `{{RUN}} build` (and `{{RUN}} lint`) before saying a change is done.
